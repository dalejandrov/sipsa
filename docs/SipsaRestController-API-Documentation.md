# SIPSA REST API Documentation

## Overview

The SIPSA (Sistema de Información de Precios y Abastecimiento del Sector Agropecuario) REST API provides access to agricultural price and supply data from various sources and aggregation levels. This API offers read-only endpoints for querying data collected from different markets and municipalities in Colombia.

### Base URL
```
http://localhost:8080/api/sipsa
```

### Response Format
All endpoints return data in a standardized paginated format:
```json
{
  "count": 150,
  "next": "http://api/endpoint?page=2",
  "prev": null,
  "pages": 15,
  "results": []
}
```

### Common Parameters
- `page`: Page number (1-based, default: 1)
- `size`: Page size (1-100, default: 20)
- `sort`: Sort field and direction (e.g., "fechaCaptura,desc")

### Date Filtering
- Single date: `fecha=2024-01-15`
- Date range: `startDate=2024-01-01&endDate=2024-01-31`

## Timezone Support

All API endpoints support timezone customization via the `X-Timezone` request header for controlling how timestamps are returned.

### Header Format
```
X-Timezone: <IANA Timezone ID>
```

### Supported Timezones
Any valid IANA timezone identifier. Common examples:
- `America/Bogota` (Colombia, UTC-5)
- `America/New_York` (US East Coast, UTC-5/UTC-4)
- `Europe/Madrid` (Spain, UTC+1/UTC+2)
- `Asia/Tokyo` (Japan, UTC+9)
- `UTC` (Coordinated Universal Time)

If the header is not provided or is invalid, the API defaults to **UTC**.

### Date Field Behavior

The API distinguishes between two types of timestamps:

#### 1. External/Historical Dates (Always UTC)
These dates originate from external systems and represent historical data points. They are **always returned in UTC** regardless of the `X-Timezone` header to ensure consistency across all clients:

- `fechaCaptura` - Original data capture timestamp
- `fechaCreacion` - External system creation timestamp
- `fechaIni` - Period start date (weekly data)
- `fechaMesIni` - Month start date (monthly data)
- `enmaFecha` - Survey/market date

**Format**: ISO-8601 with `Z` suffix (e.g., `2026-01-06T05:00:00Z`)

#### 2. System Timestamps (Client Timezone)
These dates are generated by this API system and represent operational metadata. They are **converted to the client's timezone** specified in the `X-Timezone` header:

- `fechaSincronizacion` / `fechaIngestion` - Last data synchronization timestamp
- `lastUpdated` - Last update timestamp
- `occurredAt` - Audit event timestamp
- `startTime` - Ingestion run start time

**Format**: ISO-8601 with timezone offset (e.g., `2026-01-07T00:04:03-05:00` for Bogota)

### Examples

#### Request without timezone header (defaults to UTC)
```bash
curl http://localhost:8080/api/sipsa/ciudad?ciudad=ARMENIA
```

**Response**:
```json
{
  "results": [
    {
      "fechaCaptura": "2026-01-06T05:00:00Z",
      "fechaSincronizacion": "2026-01-07T00:04:03Z"
    }
  ]
}
```

#### Request with Colombia timezone
```bash
curl -H "X-Timezone: America/Bogota" \
     http://localhost:8080/api/sipsa/ciudad?ciudad=ARMENIA
```

**Response**:
```json
{
  "results": [
    {
      "fechaCaptura": "2026-01-06T05:00:00Z",
      "fechaSincronizacion": "2026-01-06T19:04:03-05:00"
    }
  ]
}
```

#### Request with Japan timezone
```bash
curl -H "X-Timezone: Asia/Tokyo" \
     http://localhost:8080/api/sipsa/ciudad?ciudad=ARMENIA
```

**Response**:
```json
{
  "results": [
    {
      "fechaCaptura": "2026-01-06T05:00:00Z",
      "fechaSincronizacion": "2026-01-07T09:04:03+09:00"
    }
  ]
}
```

**Note**: Notice how `fechaCaptura` (external) remains constant in UTC across all requests, while `fechaSincronizacion` (system) adjusts to the requested timezone.

### 2. Ciudad (City-level Pricing Data)
**GET** `/api/sipsa/ciudad`

Retrieves price information collected at city level, including average prices per product and capture date.

#### Parameters
- `fecha`: Filter by exact capture date (YYYY-MM-DD)
- `startDate`: Filter by date range start (YYYY-MM-DD)
- `endDate`: Filter by date range end (YYYY-MM-DD)
- `artiId`: Filter by product ID (positive number)
- `fuenId`: Filter by source ID (positive number)
- `ciudad`: Filter by city name (exact match)
- `producto`: Filter by product name (exact match)

#### Query Combinations
- **By date**: `?fecha=2026-01-06`
- **By date range**: `?startDate=2026-01-01&endDate=2026-01-07`
- **By product**: `?artiId=13` or `?producto=Banano*`
- **By source**: `?fuenId=1`
- **By city**: `?ciudad=ARMENIA`
- **Combined**: `?ciudad=ARMENIA&producto=Banano*&startDate=2026-01-01&endDate=2026-01-07`

#### Examples
```
GET /api/sipsa/ciudad?ciudad=ARMENIA&startDate=2026-01-01&endDate=2026-01-07&page=1&size=20&sort=fechaCaptura,desc
```

#### Response Example

### 5. Parcial (Partial Market Data by Municipality)
**GET** `/api/sipsa/parcial`

Provides detailed market information at municipality level, including price ranges and product availability.

#### Parameters
- `fechaEncuesta`: Filter by survey date (YYYY-MM-DD)
- `startDate`: Filter by date range start (YYYY-MM-DD)
- `endDate`: Filter by date range end (YYYY-MM-DD)
- `muniId`: Filter by municipality DIVIPOLA code — **text, exact match**. Leading zeros
  are significant and preserved: `05001` and `5001` are different codes. Max 50 chars.
  A present-but-blank value returns `400`.
- `fuenId`: Filter by source ID (positive number)
- `idArtiSemana`: Filter by product/article ID (positive number) — **canonical parameter**,
  matches the `idArtiSemana` field returned in responses.
- `artiId`: Compatibility alias for `idArtiSemana` (kept because it is the product-filter
  name used by the other SIPSA endpoints). If both `idArtiSemana` and `artiId` are sent,
  they must have the same value — conflicting values return `400 VALIDATION_ERROR`.
- `muniNombre`: Filter by municipality name (exact match)
- `deptNombre`: Filter by department name (exact match)
- `fuenNombre`: Filter by source name (exact match)
- `artiNombre`: Filter by product name (exact match)
- `grupNombre`: Filter by group name (exact match)

#### Query Combinations
- **By date**: `?fechaEncuesta=2020-02-01`
- **By date range**: `?startDate=2020-01-01&endDate=2020-03-01`
- **By municipality**: `?muniId=05001` (leading zero preserved) or `?muniId=11001` or `?muniNombre=BOGOTÁ, D.C.`
- **By department**: `?deptNombre=BOGOTÁ, D. C.`
- **By source**: `?fuenId=1` or `?fuenNombre=Bogotá, D.C., Corabastos`
- **By product**: `?idArtiSemana=14` (canonical), `?artiId=14` (alias) or `?artiNombre=Aguacate*`
- **By group**: `?grupNombre=FRUTAS`
- **Combined**: `?muniId=05001&idArtiSemana=14&startDate=2020-01-01&endDate=2020-03-01`

#### Validation errors (`400 VALIDATION_ERROR`)
- `?muniId=` or `?muniId=%20%20` — blank municipality code
- `?idArtiSemana=1&artiId=2` — contradictory article parameters

## Notes
- All string filters are case-sensitive exact matches.
- Date parameters must be in ISO format (YYYY-MM-DD).
- When using date ranges, `endDate` must be greater than or equal to `startDate`.
- Pagination is 1-based.
- Default sort is descending by the primary date field of each endpoint.
- The API supports combining multiple filters for precise queries.
